## 一、RAG 的问题和基本流程

### 从问答到检索增强

机器问答（Question Answering, QA）是自然语言处理的核心任务之一。早期的研究主要聚焦于**机器阅读理解（MRC）**。以经典的 SQuAD 数据集为例，该任务向模型提供一个特定的文本段落（Context）和相关的问题，要求模型在给定的语料范围内，准确定位并提取出正确答案。这种场景属于封闭的“基于给定上下文的信息抽取和推理”，任务难度相对可控。

![SQuAD 阅读理解与多模态问答示意](assets/W12_LLM_RAG&Agent_page_002.png)

然而，真实世界的需求往往是**开放域问答（Open-domain QA）**。在这一场景下：
* 系统不再预置任何特定的段落。
* 模型必须针对用户的任意输入问题，自行从海量文档库（如整个维基百科或全网文档）中，定位相关信息并汇聚生成答案。
这更贴近现实生活中“只提问，不知道参考资料在哪”的客观规律，难度明显跨越了一个台阶。

![开放式问答示意](assets/W12_LLM_RAG&Agent_page_003.png)

**DrQA 的基本管线**

为了在工程上攻克开放域问答，Chen 等人在 2017 年推出了经典的 **DrQA** 系统。该系统首次在业界确立了**文档检索器（Document Retriever）**与**文档阅读器（Document Reader）**双层耦合的工作管线：
1. **Retriever 阶段**：接收用户问题，利用高效检索算法（如 TF-IDF）从维基百科的数十万文档中快速筛选出最相关的候选段落。
2. **Reader 阶段**：调用一个深层的神经网络，对选出的段落进行精细化阅读，定位并抽取答案实体。
这一 Retriever-Reader 框架，便是现代 RAG（检索增强生成）技术的最初雏形。

![DrQA 检索增强架构图](assets/W12_LLM_RAG&Agent_page_005.png)

![检索增强流程详解](assets/W12_LLM_RAG&Agent_page_004.png)

### 大模型为什么需要外部知识

**参数记忆的局限**

纯参数化的大语言模型（LLM）将世界知识隐式存储在模型海量的权重参数中。尽管表现出博古通今的知识面，但在真实业务落地中，这种“参数记忆”模式显露出三个根本性的缺陷：
1. **知识过时与时效瓶颈**：预训练模型具有截止日期（Cutoff Date）。截止日期之后的实时新闻、最新的医疗/法律规范或动态变动的公司财报，模型完全无法涵盖。
2. **极高的更新代价**：若想通过全量或增量预训练刷新模型的参数知识储备，需要动用高昂的算力和漫长的训练时间，这在线上商业服务中是不可承受的。
3. **不可控的“幻觉”现象**：当模型遇到自身知识库盲区或发生概率漂移时，会极其一本正经地编造虚假的事实，且无法向用户提供真实的推理和引用出处，这在医疗、金融等严肃领域是致命的。

![语言模型的局限](assets/W12_LLM_RAG&Agent_page_006.png)

![参数记忆的问题](assets/W12_LLM_RAG&Agent_page_007.png)

**外部检索的价值**

针对参数记忆的弊端，**检索增强生成（Retrieval-Augmented Generation, RAG）** 提供了系统级的解决方案：**不再强求大模型去背诵整个世界的实时变化，而是在模型回答问题的瞬间，从外部知识库检索相关的参考文档并塞入 prompt，提供给模型进行“开卷考试”**。

这带来了两大系统性优势：
* **极致的动态性**：无需频繁调整或重新训练昂贵的大模型，只需实时修改、增删检索系统背后的非结构化数据库（如上传一份最新的产品说明书），模型即可立刻获得该领域的准确答复能力。
* **高可解释性**：生成的文本可以显式标注引用的外部段落出处，支持用户一键追踪信源，极大地压制了幻觉现象，增强了系统可信度。

![利用检索技术克服语言模型的不足](assets/W12_LLM_RAG&Agent_page_008.png)

### 检索、阅读与重排

**Retriever-Reader 流程**

在现代 LLM-RAG 流程中，Retriever-Reader 演化为：
1. **用户输入**：系统接收到查询。
2. **检索阶段**：检索器把非结构化查询映射并定位到向量或词表索引中，筛出 Top-K 个参考段落。
3. **生成阶段**：将这 K 个段落连同原始查询，按照特定的模板组装成一个临时的 Context Prompt 发送给大模型。大模型充当“Reader”，理解这些材料后自回归生成回复。

![Retriever-Reader 框架](assets/W12_LLM_RAG&Agent_page_009.png)

![RAG = 检索 + 生成](assets/W12_LLM_RAG&Agent_page_010.png)

**几类检索方法**

在 Retriever 端，经历了三代核心算法的迭代演进：

1. **稀疏向量检索（如 BM25）**：主要依赖词频（TF）和逆文档频率（IDF）对 Query 和文档进行精确字符级比对。优点在于速度极快，在专有名词（如商品型号、专有人名）匹配上具有极高的精确度，但缺点是无法捕捉近义词或深层语义。
2. **稠密向量检索（如 DPR, Sentence Embeddings）**：利用深度学习模型（如双塔 Transformer 架构）将 Query 和文档分别编码为固定维度的密集向量，通过余弦相似度进行最近邻搜索。它可以实现概念级、语义级的软匹配，但对生僻专业词汇的召回较弱。
3. **多向量局部交互检索（如 ColBERT）**：克服了单向量把长文档压缩为单个向量引起的信息丢失，它保留了文档中每一个 token 的特征向量，在检索时与 Query 的所有 token 向量做交叉交互计算（Late Interaction）。这一方案召回精度极佳，但在计算速度和空间存储上开销显著增加。

![不同类型的检索器](assets/W12_LLM_RAG&Agent_page_011.png)

![快速检索器与慢速检索器对比](assets/W12_LLM_RAG&Agent_page_012.png)

**联合训练**

在高级 RAG 架构设计中，一个核心趋势是避免将 Retriever 和 Reader 孤立看待，而是进行**联合训练优化**。

其设计思想是：利用 Reader 对最终生成文本的交叉熵损失，通过反向传播来隐式引导 Retriever 向量表征模型的微调。目标是让检索器学会检索出“**对最终大模型生成正确答案最有实质帮助**”的文本，而非仅在语义上看似相近的文本，从而达成全局效能的最优配置。

![阅读器与检索器的联合训练](assets/W12_LLM_RAG&Agent_page_013.png)

![我们可以使用多少份文档？](assets/W12_LLM_RAG&Agent_page_014.png)

### 长上下文和引用问题

**长上下文位置偏差**

研究表明，盲目增加检索到的文档数量并塞满大模型的上下文窗口，并不能带来精度的线性增长。大语言模型在利用长上下文时，存在显著的“**迷失在中间（Lost in the Middle）**”现象：**大模型会高度关注 prompt 的开头部分（首因效应）和尾部（近因效应），但会严重忽略夹在 prompt 中间区域的文本。**

这意味着，如果检索器返回的真正相关信息被放在了上下文的中段，大模型在阅读时大概率会视而不见。这要求 RAG 必须配合使用**重排模型（Reranker）**，重新计算相关度，并将高价值段落排在最前和最后。

![LLM 无法关注整个上下文](assets/W12_LLM_RAG&Agent_page_015.png)

![LLM 无法处理大量文档](assets/W12_LLM_RAG&Agent_page_016.png)

**实时搜索**

将 RAG 的本地文档库替换为实时的互联网搜索引擎，便构成了 Perplexity 等新一代 AI 搜索工具。它能够在接收用户请求后，由系统后台多批次调度搜索引擎、抓取高分网页，将其拼装成上下文供给模型，实现了在实时开放网络环境下的信息即时整合。

![具备网络搜索功能的 LLM](assets/W12_LLM_RAG&Agent_page_017.png)

**引用校验**

即使大模型在生成时参考了给定的材料，它们所生成的引用指针（Citations，如 `[1]`）也可能发生幻觉，表现为“**引用的文档与它所支持的断言根本对不上**”。

为了缓解引用幻觉，系统设计通常会叠加多重校验机制：
* **硬性相似度约束**：对生成句与被引用的原始文档做语义相似度或 N-Gram 覆盖计算，如果不满足阈值则强行剔除引用。
* **双向校验器（Self-RAG）**：引入一个专门的反思模型，对生成的每句话进行质询，评估其是否能够被检索到的文本直接推导（Entailment），确保引用的真实性。

## 二、Agent 的基本循环

### 从目标到行动

**AI Agent（智能体）** 代表了人机交互逻辑的彻底升华：

* **传统交互模式**：人类给出细化到具体操作步骤的命令，大模型单步执行。
* **Agent 模式**：人类仅提供一个宏观的终极目标（Goal），智能体自身去分析目标、拆解步骤、调用工具、遭遇失败后自行修改规划，直到自动达成目标。

这使得 AI 从一个简单的辅助聊天工具演化为了可以独立执行业务流的数字员工。

![AI Agent 与传统 AI 的对比](assets/W12_LLM_RAG&Agent_page_022.png)

**Goal-Action-Observation**

所有的 AI Agent 在逻辑上都遵循经典的 **Goal $\rightarrow$ Action $\rightarrow$ Observation** 反馈控制闭环：
1. **Goal（目标设定）**：系统接收到要达成的高层目标。
2. **Action（动作执行）**：智能体经过推理，调用外部手段（如执行一段 SQL、进行一次 Web 搜索）输出一个具体的动作。
3. **Observation（环境观察）**：智能体收集外部环境对动作的反馈，更新自己当前的推理认知状态，并据此决定下一个动作，循环往复。

这使得 Agent 具备了在动态环境下的自我纠偏与主动决策能力。

![Agent 基本循环](assets/W12_LLM_RAG&Agent_page_023.png)

![AlphaGo 作为 Agent 示例](assets/W12_LLM_RAG&Agent_page_024.png)

**用语言模型驱动 Agent**

传统的智能体开发通常依赖复杂的强化学习（RL），但其最大的痛点在于泛化性弱。**大语言模型（LLM）的出现为构建通用智能体提供了理想的内核。**

在大模型驱动的 Agent 框架下，高层的 Goal 被翻译为文字，而 Agent 的每一个 Action 以及环境的反馈（Observation）都表现为一连串追加进 Context 中的文本。模型在这个不断延长的“对话接龙”历史中，利用其预训练所习得的逻辑链条和通用常识，生成下一个动作的描述。这种模式省去了为每个细分任务单独进行强化学习调优的昂贵开销。

**五个组成部分**

一个工程可用的 LLM 语言智能体必须包含以下五大核心支柱：

1. **LLM 核心大脑**：负责通用的常识建模、多步骤的文本生成和综合逻辑调度。
2. **规划与反思层**：包含 CoT, ReAct 以及 Reflexion 反思回路，负责拆解目标与修正计划。
3. **记忆系统**：负责长期或短期存取交互中的关键变量和历史结论。
4. **工具库（Tools）**：包括代码执行器、计算器、检索系统等，用于帮助模型与外界产生物理交互。
5. **外部环境（Environment）**：智能体赖以生存的宿主系统，如操作系统控制台、Web 浏览器或者沙箱环境。

### 推理、行动和反思

**推理的作用**

推理是智能体在复杂环境中生存的灵魂。如果智能体缺乏推理，仅仅采用粗暴的“条件反射（Action-only）”映射，一旦环境状态超出训练范围，系统就会立刻崩溃。

推理使智能体能够将复杂的现实物理问题在隐空间中映射并展开，通过模拟各种可能的执行后果，最终对准真实的目标。同时，如果仅做纯粹的“闭门推理”，由于其全部信息来源于内部的非精准参数记忆，很容易引发事实性偏差。

![推理对智能体的帮助](assets/W12_LLM_RAG&Agent_page_036.png)

![只靠推理的局限](assets/W12_LLM_RAG&Agent_page_037.png)

**ReAct 框架**

为了将推理和实际工具调用有机结合，**ReAct 框架** 被提了出来。它将执行步骤组织为 **Thought $\rightarrow$ Action $\rightarrow$ Observation** 的紧密迭代：
* **Thought**：生成当前步骤的推理分析，明确当前需要解决的子任务与需要的外部工具。
* **Action**：向环境发射具体的指令动作，调用指定的工具接口。
* **Observation**：接收并读取外部工具返回的数据，拼装回上下文。
在下一个计算循环中，大模型会基于最新拿到的 Observation 进行新的 Thought 推理。这种“边推理、边操作、看结果、再推演”的逻辑，使智能体具备了极高的数据纠错与主动求证能力。

![ReAct 示例](assets/W12_LLM_RAG&Agent_page_038.png)

![ReAct 与 CoT、SC 的对比](assets/W12_LLM_RAG&Agent_page_039.png)

**反思与纠错**

为了防范 Agent 陷入死循环，需要引入更高阶的反思和校验手段：
* **自一致性过滤**：采样生成多条完全不同的推理路径，通过最终答案投票，剔除低质量漂移。
* **Reflexion 反思环**：当智能体遇到多次操作失败或触发系统报错时，Reflexion 机制会中止当前执行流，强制大模型总结当前的执行轨迹，指出先前决策的失误之处，生成一段书面形式的反思经验记录。这段反思记录会被存入长期记忆库，在接下来的计划生成时作为前置输入的一部分，以指导智能体完美避开之前的陷阱。

### 多智能体协作

为了在解决高难度任务时获得更高的上限，可以部署**多智能体辩论**或**多智能体协同系统（如 Magentic-One）**。多智能体辩论通过让多个大模型角色就同一个命题展开观点陈述和交锋，最终收敛出高可信度的推导路径。而在协同场景中，一个总的 Orchestrator（协调器）会将总目标切分为多个任务包，并动态派发给网页 Agent、终端 Agent 或数据 Agent 分头解决，极大地提升了处理大型端到端任务的系统稳定性。

## 三、记忆与工具

### 记忆如何写入和读取

智能体的记忆系统负责在多轮交互中沉淀经验。在系统工程上，记忆通常借鉴人类的记忆体系进行形式化重构，主要包含三类长时记忆：情景记忆、语义记忆与程序性记忆。

![记忆类型分类](assets/W12_LLM_RAG&Agent_page_048.png)

**事件流记忆**

斯坦福的虚拟小镇实验（Generative Agents）指明了记忆管理的痛点：在模拟村民的长生命周期运行中，每天产生的事件流（文字流）极为漫长，远远超出了大模型有限的上下文窗口容量。即便强行堆砌上下文，大模型也会因为高频的信息稀释，而无法对当前突发的事件做出合理反应。因此，构建一个具备增量式写回和高精度召回的记忆管理机制是必不可少的。

![生成式 Agent 虚拟村庄](assets/W12_LLM_RAG&Agent_page_049.png)

![对记忆的需求](assets/W12_LLM_RAG&Agent_page_050.png)

**三类记忆**

1. **情景记忆（Episodic Memory）**：
   * **写入**：采用仅追加模式，将智能体感知到的所有事件（如“下午 3:00 咖啡壶溢水了”）作为原始日志依次记入时间轴数据库。
   * **读取（检索）**：基于一个多因子的评分函数进行召回计算。其评测得分综合了三个不同的物理维度：
     $$\text{Score} = \alpha \cdot \text{Recency（时间远近）} + \beta \cdot \text{Importance（事件重要度）} + \gamma \cdot \text{Relevance（与当前话题语义相似度）}$$

![情景记忆](assets/W12_LLM_RAG&Agent_page_051.png)

2. **语义记忆（Semantic Memory）**：智能体对原始日志进行定时合并和总结（Reflection），提炼成更一般的概念和对世界的全局性理解（如“爱丽丝喜欢在下午喝拿铁咖啡”），并将这些结构化语义概念保存在记忆网络中。

![语义记忆](assets/W12_LLM_RAG&Agent_page_052.png)

3. **程序性记忆（Procedural Memory）**：主要关注智能体对技能的固化。智能体可以通过将执行成功的代码段或者操作脚本保存下来（如 Voyager 智能体），在后续面临相同任务时直接检索并调用这些已成型的代码技能包，实现高效复用。

![程序性记忆](assets/W12_LLM_RAG&Agent_page_053.png)

**MemGPT 的分层内存**

**MemGPT** 极具创意地引入了传统操作系统中**虚拟内存管理**的设计思想。它为智能体设计了分层的存储池：

* **主内存（类似于 RAM，即当前 Prompt 上下文）**：只保留最核心、最即时的交互状态。
* **外部内存（类似于硬盘，包含非结构化和结构化数据库）**：存放海量的长期记忆、事件历史和大宗文档。
MemGPT 赋予大模型使用特定 API（如 `memory_read`, `memory_write`）的权限。大模型在推理过程中，如果发现当前主内存中的关键数据缺失，可以主动发起系统调用去硬盘调取相关记忆载入主存；或者在得到核心结论后，主动将其持久化写回到外部数据库。这打破了物理上下文长度对智能体运行生命周期的限制。

![MemGPT 架构](assets/W12_LLM_RAG&Agent_page_054.png)

### 工具调用怎么学习

**ToolkenGPT**

如何让大语言模型更流畅地调用外部工具？**ToolkenGPT** 提出了一个独特的设计：**将每个备选的 API 工具，直接映射为大模型分词词表里的一个特殊的 Token（称为 Toolken）**。

在预测文本接龙时，一旦模型输出了该特定 Toolken，系统就会拦截生成流，识别出大模型当前的工具调用意图。接下来，系统会把输入流重定向到该工具对应的参数填充 Prompt 中，收集大模型生成的调用参数，执行工具，并将结果拼接回上下文继续生成。这种将工具与词汇表无缝融合的方案，使得工具调用变得像吐字一样自然。

![ToolkenGPT](assets/W12_LLM_RAG&Agent_page_056.png)

**Toolformer**

**Toolformer** 则是工具调用向自主学习演进的典范。它证明了大模型可以在无监督下，通过极其有限的少量示例，自主学会“何时、何地、以何种参数”调用 API：
1. **启发式采样**：对于原始语料，模型在文本中随机插入 API 调用尝试。
2. **过滤与过滤**：真正执行这些 API 并获取返回值（如计算器计算 `3+5=8`）。如果加入该 API 调用和计算结果能够明显降低后续文本预测的 Loss（即该工具能够提供实质的背景信息支持），则将这一组 API 插入样本保留下来。
3. **微调收敛**：在大批经过上述筛选的“包含 API 调用的文本”上对模型进行微调，使其自发学会何时发起检索、何时打开计算器、何时翻阅日历。

### 一个极简编程 Agent

在代码开发实战中，构建一个极简编程 Agent 的闭环只需实现三个基本函数：
1. `query_lm`：让大模型思考，基于当前对话历史，推理输出下一步的自然语言描述及嵌入其中的 Action 指令。
2. `parse_action`：文本解析器，从大模型吐出的混合段落中提取出真正的 Action 指令（如一段 Bash 命令）。
3. `execute_action`：运行环境，把 Action 送入本地 Shell 或 Docker 沙箱安全执行，捕获其标准输出 Stdout 并转化成 Observation 反馈送回。

这三个核心函数的环环相扣，构成了整个智能体生生不息的执行循环。
