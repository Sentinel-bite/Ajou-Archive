## 一、KV Cache 为什么重要

### 缓存复用与显存增长

在使用大语言模型进行推理生成时，自回归的生成范式带来了一个显著的性能瓶颈。由于模型每次生成一个新 token 都需要依赖前面的全部上下文，如果在每一步中都对整个历史序列从头计算 Query、Key 和 Value，会导致注意力得分的计算量随着文本长度 $N$ 呈二次方 $O(N^2)$ 爆发式增长。这其中包含了大量的重复矩阵乘法计算。

![自注意力中每个新 token 关注所有已生成 token](assets/W10_LLM_KVCACHE_page_002.png)

为了解决这种不必要的冗余计算，业界普遍引入了 **KV Cache（键值缓存）** 机制。该机制的核心思想在于“以空间换时间”：在生成新 token 的每一步中，不再重新计算所有已生成历史 token 的 Key 和 Value 向量，而是将这些已计算出的中间结果永久保存在 GPU 显存中。当自回归模型每次解码出新的 token 时，只需为当前单步计算其对应的 $q, k, v$ 向量，接着将新计算出的 $k$ 和 $v$ **拼接**到已保存的 KV 历史缓存中。最后，用当前 $q$ 与更新后的完整 Key/Value 缓存做注意力点积计算。

这一优化成功地将单步推理的计算复杂度从二次方级别 $O(N^2)$ 降低到了一次方线性级别 $O(N)$，使多轮生成推理的耗时大大降低。

![KV Cache 工作原理示意图](assets/W10_LLM_KVCACHE_page_003.png)

![KV Cache 直接复用已计算的 K 和 V](assets/W10_LLM_KVCACHE_page_004.png)

**显存增长问题**

尽管 KV Cache 在很大程度上提升了计算速度，但它也带来了另一个严峻的问题——显存容量的极速膨胀。由于历史缓存的数据量与序列长度呈线性正相关，对于长上下文场景（如 32K 或 128K 长度的窗口），存储大批量的历史 K 和 V 矩阵可能吞噬数十甚至上百 GB 的显存空间。这种巨大的显存足迹严重制约了模型推理的并发吞吐能力，并经常导致系统发生 Out-Of-Memory（OOM）崩溃。这促使学术界和工业界去探索各种降低 KV Cache 显存占用的设计方案。

![KV Cache 随上下文长度线性增长](assets/W10_LLM_KVCACHE_page_005.png)

### 注意力变体的压缩办法

**GPU 访存约束**

与一般的存储架构相同，GPU 采用了一种多层级的分化体系，主要包括极小极快的片上 SRAM（静态随机存取内存）以及容量极大但总线带宽有限的外部 HBM（高带宽显存）。当自回归生成在 Decode 阶段迭代时，每一次注意力计算都需要从慢速的 HBM 调取之前缓存的所有历史 K 和 V 数据，装载到片上的 SRAM 参与计算。随着 KV Cache 的规模不断增加，SRAM 和 HBM 之间的高频访存数据搬运成为了比计算本身更加致命的带宽瓶颈。因此，减少要在 HBM 存储和搬运的 KV Cache 尺寸是实现高吞吐模型推理的必经之路。

![SRAM 与 HBM 存储层级示意](assets/W10_LLM_KVCACHE_page_006.png)

**MQA 与 GQA**

为了从架构上直接削减 K 和 V 的体量，业界提出了两款被广泛应用的注意力替代结构：

* **Multi-Query Attention (MQA)**：在传统的 Multi-Head Attention（MHA）中，每个 Query Head 都拥有对应且独立的 Key Head 与 Value Head。而 MQA 的设计极其激进：**所有的 Query Head 在计算时都强制共享同一组单独的 Key 和 Value Head**。这一改动能够将 KV Cache 瞬间缩减为原先的 $1/h$（ $h$ 为 Head 数量），极大地削弱了显存读写负荷，但代价是模型表达能力下降，可能引起精度的损失。

![Multi-Query Attention 结构对比](assets/W10_LLM_KVCACHE_page_007.png)

![MQA：多个 Query Heads 共享一套 K/V Heads](assets/W10_LLM_KVCACHE_page_008.png)

* **Grouped-Query Attention (GQA)**：作为 MHA 和 MQA 的一种折中方案，GQA 引入了分组共享策略。它将多个 Query Head 划分为若干个分组，**处于同一个分组内部的所有 Query Head 共享一对指定的 K 和 V 向量**。例如 LLaMA-2 70B 模型将 64 个 Query Head 分为了 8 个不同的组，使得每组包含 8 个 Query Head 并共享一套独立的 K/V Head。GQA 在保证极高推理效率的前提下，最大程度弥补了 MQA 在逻辑表达能力上的折损，成为了现今最为主流的模型默认架构配置。

![Grouped-Query Attention 分组共享示意](assets/W10_LLM_KVCACHE_page_009.png)

**MLA 压缩思路**

由 DeepSeek 提出的 **Multi-head Latent Attention (MLA)** 将 KV Cache 优化推向了新的高度。它没有直接减少 Head 数量，而是采用**低秩投影压缩**机制：在数据写入 KV 缓存时，模型不再保存各个 token 完整的 K 和 V 表示，而是将每个 token 本身的隐藏状态 $h$ 经过一个下投影矩阵 $W_{DKV}$ 压缩成一个低维的 latent 向量 $c$ 写入缓存。在 Decode 阶段需要计算注意力时，模型再通过上投影矩阵 $W_{UK}$ 和 $W_{UV}$ 从低维向量 $c$ 实时重构和解压出各个头需要的 K 和 V 表示。

![MLA 基本原理：压缩 KV 到 latent 向量](assets/W10_LLM_KVCACHE_page_010.png)

MLA 的数学运行机制如下：
1. **下投影压缩**：利用投影矩阵将 $h_t$ 投影到低维潜空间 $c_t^{KV}$，只将极低维度的 $c_t^{KV}$ 存入 KV 缓存。
2. **片上解压与计算**：在进行 Attention 计算时，直接在 SRAM 中结合上投影矩阵将当前 Query 与 $c_t^{KV}$ 做乘法，即时重构出各 Head 对应的 K 和 V 向量。

通过这种设计，MLA 在保持甚至超越多头注意力信息表达精度的同时，把需要高频读写的 KV 显存开销限制在了与 GQA 类似甚至更低的极小物理尺寸上。

## 二、长上下文中的缓存管理

### 滑动窗口与关键 token

随着推理序列增长，除了通过维度压缩减少显存外，还可以通过限制注意力的依赖窗口大小来直接阶段化 KV 缓存：

* **Sliding Window Attention（滑动窗口注意力）**：强制每个 token 在计算注意力时仅将视线投向最近的 $W$ 个 token。这使得 KV 缓存的总体大小被死死限制在 $W$ 的范围，从而不再随长上下文无节制膨胀。像 Mistral 7B 模型就在单层应用了滑动窗口设计，但通过叠加多层，较浅层捕获的信息能够被逐步向上传播，从而获得超出 $W$ 的累积全局感受野。

![Mistral 7B 的 Sliding Window Attention](assets/W10_LLM_KVCACHE_page_017.png)

![GPT-OSS 混合注意力策略](assets/W10_LLM_KVCACHE_page_018.png)

* **StreamingLLM 与 Attention Sinks**：研究发现，在自回归推理中存在一个独特的 **Attention Sinks（注意力汇）** 现象：模型在计算长序列注意力时，无论开头的若干个 token 与当前上下文是否具备语义联系，都会分摊到极高强度的注意力权重。基于此，StreamingLLM 设计了一种特别的固定大小缓存维护策略：**永久保留序列开头的头几个 token（一般为前 4 个），再结合当前的滑动窗口保留最近的 token，中间部分的 token 直接予以丢弃**。这一方案保证了注意力权重的分流稳定，使得模型能够支持几乎无限长的流式推理而显存保持恒定。

![StreamingLLM 固定缓存策略示意](assets/W10_LLM_KVCACHE_page_019.png)

**动态裁剪**

不同于盲目截断，动态裁剪（KV Cache Pruning）尝试识别并过滤低价值的缓存，以释放空间：

* **Scissorhands**：基于一种长期记忆假设——如果在过去的生成迭代中，某些 token 被分配到的注意力权重长期处于极低状态，那么它们在未来的生成周期中也几乎不可能被再次关注。因此，算法会在迭代中周期性检测并完全擦除这些低关注度 token 对应的 K 和 V 缓存。
* **H2O (Heavy-Hitter Oracle)**：基于“重击者”选择策略，系统会维护一个关于注意力得分的追踪累积器，筛选出长期占据高频热点的 Heavy Hitters，在显存超限时仅保留这些热点 token 和最近生成的 token，其余中间的非关键缓存直接执行动态释放。

实验数据证实，这两种基于价值判断的精细化裁剪，能够在仅保留 20%~30% 的 KV 缓存的前提下，近乎无损地完成长文本阅读理解等各类复杂生成任务。

![Scissorhands 与 H2O 裁剪策略对比](assets/W10_LLM_KVCACHE_page_020.png)

![Scissorhands 压缩效果：横轴为压缩倍率，纵轴为 perplexity/准确率](assets/W10_LLM_KVCACHE_page_021.png)

### Prompt Caching

**跨会话复用**

在真实的线上大模型服务中，不同的用户请求或是多轮对话交互之间，经常共享非常多的文本前缀。例如系统提示词（System Prompts）、预置的 Agent 工具描述列表或多轮对话的公共历史。

**Prompt Caching（提示词缓存）** 从系统调度层面提供了极高价值的优化：如果前后两个不同的推理请求其 prompt 的前半部分内容完全一致，系统就可以在内存中直接共享和复制先前请求已经算好的 KV Cache，省去了再次对公共前缀进行重复 Prefill 计算的开销。

![跨对话 Cache 复用示意](assets/W10_LLM_KVCACHE_page_022.png)

![AI Agent 场景下的高 Cache 命中率](assets/W10_LLM_KVCACHE_page_025.png)

为了最大化提升 Prompt Caching 的命中概率，系统和工程师会遵循以下设计原则：
1. **排布优化**：必须将完全固定、几乎不发生改变的前置定义（如 System Prompts, RAG 的参考背景文档）集中放置在 Prompt 的最前端，而将动态发生变化的内容（如最新的用户问题、即时的外部输入）集中安排在 Prompt 的最后端。

![Prompt 排列优化策略](assets/W10_LLM_KVCACHE_page_026.png)

2. **模板规范化**：通过将可变的用户指令规范化、模板化（例如对请求语句“帮我订一张从 [出发地] 到 [目的地] 的机票”），提高前缀片段的重复命中能力。

![Prompt 模板化提高 Cache 命中](assets/W10_LLM_KVCACHE_page_027.png)

**Prefill 阶段收益**

大语言模型的单次推理可以划分为计算密集型的 Prefill 阶段（并行处理整个 Prompt 输入）与内存总线带宽密集型的 Decode 阶段（自回归逐 token 输出）。

Prompt Caching 在根本上优化了 Prefill 阶段的响应开销。一旦触发 Prompt 缓存命中，系统可以直接调取历史的键值缓存，从而跳过对长前缀的繁重注意力计算，将系统的首字延迟（Time to First Token, TTFT）降低到极致，同时也大幅节约了在线云服务的计算算力。

## 三、MoE 的基本机制

### 稀疏激活

在典型的 Transformer 模块设计中，包含了自注意力（Self-Attention）层以及前馈神经网络（Feed-Forward Network, FFN）层。典型的 FFN 层的计算可以描述为：

$$H = \text{LayerNorm}(\text{ReLU}(ZW_1)W_2 + Z)$$

在这个经典设计中，每个传入的 token 都会激活 FFN 内所有的参数，其计算开销会随着模型隐藏层特征维度的扩张呈二次方速度递增。然而在深层大模型中，FFN 层占据了整个系统几乎 60% 以上的参数总量，是推理计算的主要耗时大户。

![Transformer 模块结构回顾](assets/W10_LLM_KVCACHE_page_032.png)

![普通 FFN 层的计算特点](assets/W10_LLM_KVCACHE_page_033.png)

![FFN 是参数量最大的组件](assets/W10_LLM_KVCACHE_page_034.png)

**混合专家模型 (Mixture of Experts, MoE)** 的引入打破了这一“全量计算”的约束。其基本原理是：**放弃使用单个庞大的 FFN 层，转而并行部署多个小型的 FFN 层（每个小型 FFN 被称为一个“专家 Expert”）**。在此基础上，系统通过引入一个轻量级的门控网络（Router，路由器），为每一个输入的 token 选择并激活其中最匹配的少数几个专家。

这实现了一种极其高效的“**稀疏激活 (Sparse Activation)**”：模型的名义参数总量（静态参数量）可能非常庞大，但在每一次推理的计算路径上，真正被激活参与浮点数运算（FLOPs）的专家参数量（激活参数量）只是其中很小的一部分。这帮助 MoE 架构突破了“参数规模增加必然引发计算延迟增加”的传统瓶颈。

![MoE 核心思想：多专家稀疏激活](assets/W10_LLM_KVCACHE_page_035.png)

### 门控与路由

在主流的 Top-2 稀疏门控模型设计中，对于一个输入向量 $X$，其在 MoE 层内部计算的详细数学步骤如下：

1. **计算专家分值**：利用路由器门控权重 $W_G$ 将输入映射到各专家的概率 logits 上，并利用 Softmax 归一化：

$$G = \text{Softmax}(W_G X)$$

2. **Top-K 筛选**：针对概率分布 $G$，贪婪地筛选出分值最高的前 $k$ 个专家的序号索引集合：

$$I = \{i_0, i_1, \dots, i_{k-1}\} = \text{TopK}(G, k=2)$$

3. **路由权重重新归一化**：为了消除未选中专家的残余概率对输出量纲的扭曲，必须对被选中的这 $k$ 个专家的路由权重进行再次归一化：

$$s_0 = \frac{G_{i_0}}{G_{i_0} + G_{i_1}}, \quad s_1 = \frac{G_{i_1}}{G_{i_0} + G_{i_1}}$$

4. **加权专家的输出求和**：将输入向量 $X$ 分别送入对应的专家 FFN 进行独立运算，并使用重构后的权重进行乘加：

$$Y = s_0 \cdot \text{FFN}_{i_0}(X) + s_1 \cdot \text{FFN}_{i_1}(X)$$

通过这种门控选择，不同语义特征的 token 能够进入最擅长它的专家网络进行处理。

![MoE 层详细结构与计算流程](assets/W10_LLM_KVCACHE_page_036.png)

**路由例题**

为了使路由的计算过程更加清晰，我们可以通过一个简单的 Top-2 路由例题来剖析各个计算步骤：

**初始条件**：
* 输入特征向量 $X = [2, 1]^T$。
* 备选专家数量为 4 个（$E_0, E_1, E_2, E_3$）。
* 路由门控权重矩阵：

$$W_G = \begin{bmatrix} 1 & 0 \\ 0 & 1 \\ 1 & 1 \\ -1 & 1 \end{bmatrix}$$

* 每个专家的 FFN 算式均定义为：$\text{FFN}_i(X) = W_{2,i} \cdot \text{ReLU}(W_{1,i} X)$。

**计算推导**：
1. **计算 Router Logits**：
   $$W_G X = \begin{bmatrix} 1\times2 + 0\times1 \\ 0\times2 + 1\times1 \\ 1\times2 + 1\times1 \\ -1\times2 + 1\times1 \end{bmatrix} = \begin{bmatrix} 2 \\ 1 \\ 3 \\ -1 \end{bmatrix}$$
2. **计算 Softmax 权重分布**：
   $$e^G = \begin{bmatrix} e^2 \\ e^1 \\ e^3 \\ e^{-1} \end{bmatrix} \approx \begin{bmatrix} 7.39 \\ 2.72 \\ 20.09 \\ 0.37 \end{bmatrix}, \quad \text{Sum} \approx 30.57$$
   $$G_{\text{prob}} = \text{Softmax}(W_G X) \approx \begin{bmatrix} 0.242 \\ 0.089 \\ 0.657 \\ 0.012 \end{bmatrix}$$
3. **选择 Top-2 专家**：
   筛选最大的两个概率值对应的索引：
   * 第一名：专家 2 ($E_2$)，分值 $0.657$
   * 第二名：专家 0 ($E_0$)，分值 $0.242$
4. **再次归一化路由分值**：
   $$\text{Sum}_{\text{Top2}} = 0.657 + 0.242 = 0.899$$
   $$s_{E_2} = \frac{0.657}{0.899} \approx 0.731, \quad s_{E_0} = \frac{0.242}{0.899} \approx 0.269$$
5. **计算最终专家网络合并输出**：
   $$Y = 0.269 \cdot \text{FFN}_0(X) + 0.731 \cdot \text{FFN}_2(X)$$

## 四、Transformer 中的 MoE 变体

### 集成方式

在经典的 Transformer 模块集成 MoE 时，其做法十分直观：**保留模型原本的 Self-Attention 结构不变，而将模块中的前馈 FFN 层直接替换为 MoE 专家路由层**。这样，整个 Transformer Block 在运行自注意力整合后，通过门控路由将各个 token 的表征分配给不同的计算专家。

![Transformer + MoE 集成方式](assets/W10_LLM_KVCACHE_page_039.png)

![FFN 替换为 MoE 层的架构图](assets/W10_LLM_KVCACHE_page_040.png)

这一设计在工业界模型构建中展现了极高的工程效能潜力：
* **GLaM 架构**：该千亿级模型拥有 1.2 万亿名义参数，但由于应用了 MoE 稀疏路由，在每步前向推理中仅需要激活约 960 亿参数，这使得它仅需使用 GPT-3 约 **1/2** 的训练算力，即可在多项自然语言测评中战胜 GPT-3。
* **DeepSpeed-MoE 优化**：微软的实验结果表明，在同等硬件开销下，一个拥有 520 亿总参数的 MoE 模型（每次推理激活 13 亿参数）相比传统的 67 亿 Dense 模型，其训练和推理的算力利用效率大幅拉升，同时获得了极佳的精度性价比。

![GLaM 与 DeepSpeed-MoE 效率对比](assets/W10_LLM_KVCACHE_page_041.png)

### 共享专家与混合头

DeepSeek-V3 在传统稀疏激活 MoE 的基础上作出了进一步的升级，提出了**共享专家（Shared Expert）** 与 **路由专家（Routed Expert）** 协同的双轨机制：

在典型的路由 MoE 中，由于门控决策的贪婪性，容易产生局部专家偏向或是路由不稳定的现象。DeepSeek-V3 的解决策略是：
* **共享专家**：每个 token 无论其语义特征如何，都会无条件通过这组固定的共享 FFN 模块（类似于提供一个底座语义和共性特征捕获器）。
* **路由专家**：各 token 经由门控网络在独立的路由专家池中筛选，提取更专业的个性化特征。

其数学表征为：

$$Y = \text{SharedFFN}(X) + \sum_{i \in \text{Routed}} s_i \cdot \text{Expert}_i(X)$$

这种融合了“共性底座 + 特性分支”的改进极大加强了 MoE 模型内部多专家协作的稳定性，避免了单个路由专家的过载与冲突，提供了更高的模型收敛性能。

![DeepSeek-V3 共享专家 + 路由专家架构](assets/W10_LLM_KVCACHE_page_042.png)

![DeepSeek-V3 MoE 计算例题](assets/W10_LLM_KVCACHE_page_044.png)

**混合头注意力**

受到 MoE 在 FFN 维度优化的启发，近年来也有研究尝试将稀疏路由思想向注意力机制的注意力头（Attention Heads）进行扩展，从而演生出了 **Mixture of Heads (MoH，混合头部注意力)** 架构：

在 MoH 中，注意力头被划分为：
* **共享头部（Shared Heads）**：每个 token 默认无条件参与注意力合并。
* **路由头部（Routed Heads）**：在推理时，门控网络根据 query 和 key 的特征分布，按需激活并计算部分的注意力头分量。

这一技术旨在进一步压榨注意力头内部计算的冗余，是 MoE 稀疏激活思想从 FFN 领域迈向 Attention 计算深水区的又一次成功探索。

![混合头部注意力 (MoH) 架构](assets/W10_LLM_KVCACHE_page_043.png)
